# Mamitsu imports

Implementation checkpoint: November 4, 2026. Requested provider: [Mamitsu](https://usemamitsu.com/docs). This supersedes the earlier proposed direct acquisition/Gemini route for the first usable importer.

## Behavior and contract

An invited, verified account can submit a public Instagram Reel or a YouTube watch/Shorts/youtu.be link alongside manual recipe creation. Tracking parameters are removed; HTTPS hosts and content IDs are allowlisted. Instagram photo/carousel `/p/` posts are deliberately not admitted: the documented photo pricing has no documented maximum photo count from which to reserve a safe upper bound. No source cookies, direct creator-media downloads, signed URLs, thumbnails or generated dish images are used by this integration.

`POST /api/imports` persists a receipt before returning 202. One Next.js `after` task atomically claims it and makes one bounded server-only request to the fixed Mamitsu endpoint. `GET /api/imports` lists owner-scoped receipts with pagination and a secret-free configuration flag; the form checks that flag before enabling submission and explains unavailable setup beside the controls; `GET /api/imports/:id` restores a receipt; `DELETE` cancels an unclaimed receipt; `POST /api/imports/:id/save` saves a reviewed recipe. Every operation verifies membership and account scope; writes enforce exact-origin CSRF checks. Data and errors are private/no-store. Error messages omit provider bodies and credentials.

`apat-recipe-v1` uses a restricted JSON Schema generated from a Zod extraction contract. Unsupported string-length keywords are omitted only from the provider schema; local length, range and array checks remain mandatory. All fields are required, with nullable scalar facts. Ingredients retain their original phrase, amount/range/unit and caption/audio/visual evidence; steps retain evidence and nullable timestamps. Missing ingredient/step collections reject the draft as unsuitable for the notebook. Language is preserved, with `und` when unknown. Unknown title uses a clearly warned notebook fallback. Evidence is a provider claim requiring human checking, not independently verified acquisition evidence.

IDs, canonical source URL, provider, schema version and extraction reference are assigned by the server. A reviewed save transaction preserves the extracted draft as `recipes.original`, with the user's corrections in `recipes.edited`. Edits and saving do not call Mamitsu. Saved import receipts are hidden from the visible status list because their recipes already appear in the notebook. The server retains those receipts for credit accounting and deduplication; pending/review/failure states and older-page navigation remain accessible. Existing manual recipes remain compatible. Recipe amount ranges display correctly, and scaling is disabled when the source serving count is unknown.

## Credit and recovery policy

The provider documents a 90-second timeout, video limits of five minutes for Instagram and two hours for YouTube, and charges when the model is reached, including extraction failures. Requests use a 95-second local deadline, a 512 KiB response cap and a 200 KiB recipe cap. The route requests a 120-second function duration, which must be supported by the deployed account/runtime.

Each admission reserves a conservative maximum: **5 credits per Instagram Reel; 28 per YouTube video** (five initial one-minute blocks plus 23 five-minute blocks). These are upper-bound accounting holds, not actual measured charges. The provider response does not document actual credit usage. Successful and possibly charged failures retain the full conservative hold until an operator reconciles them with Mamitsu usage. Limits are lifetime ceilings for this database, not daily/monthly buckets; changing a ceiling does not reset history.

A database transaction advisory lock serializes admission across server instances. It enforces configured total/per-owner credit ceilings, two concurrent global imports, one per owner, 20 attempts/hour globally and five/owner. Unknown paid outcomes count as active. The owner key is unique. Canonical source deduplication also blocks new keys for active, uncertain, successful or charged failed requests. Only a confirmed pre-model failure or an unclaimed cancellation allows a new explicit attempt. No transport/model/automatic paid retries are enabled.

`queued → extracting → needs_review → saved`, with `failed`, `cancelled` and `outcome_unknown` branches. Claim and queued cancellation race through conditional SQL updates. Entitlement and the kill switch are rechecked before claim. Disabling imports does not prevent reading/saving completed drafts. A revoked member cannot read/save a result; an already submitted attempt still settles internally under its recorded owner.

**Runtime limitation:** `after` keeps work independent of the browser request, but is not a durable retrying worker. A server interruption can lose dispatch or settlement. After three minutes, an unclaimed receipt expires/cancels and releases its hold; a claimed receipt becomes `outcome_unknown` and retains its hold. Owner reads reconcile these stale states. No automatic replay occurs. Stale receipts from inactive owners may continue to block global capacity until an operator reconciles them. This is a bounded preview slice, not completion of the durable-worker/product acceptance gate.

No external media is stored, so there is no app-owned media cleanup queue. Draft/evidence retention matches the existing private recipe storage policy; full account erasure/retention automation remains a beta-release task.

For an uncertain/charged failed result, use the extraction reference to inspect Mamitsu Usage. Do not resubmit or release a hold on the basis of a timeout. Reconcile the exact row and provider outcome before an approved database adjustment; no public reconciliation/admin endpoint exists. A settled draft can be installed only after validating the same source/schema/owner. Confirm actual spend before reducing conservative held credits. Deleting evidence or resetting the ledger is not a recovery procedure.

5. Deploy/redeploy only the approved preview, verify login and membership, and run explicitly approved real Reel and YouTube trials. Check the same receipts, provider usage, reload/review/save/export and source evidence. Do not claim mocked browser/PGlite results establish these live outcomes. Production rollout remains separate.

## Verification boundaries

Unit tests use authored provider envelopes and injected transports; they make no paid requests. PGlite runs the real Drizzle migrations and services, covering PostgreSQL admission/ownership/settlement/review saves and runtime grants. This is not Neon integration evidence. Playwright tests run against the built app with authored HTTP fixtures on desktop and mobile Chromium; they are not real Google login, Mamitsu extraction, mobile Safari or Vercel verification.

Read-only inspection of the user's existing Mamitsu usage and successful request schema informed the contract. No creator caption/media was copied into repository fixtures or logs. Their earlier failures demonstrate that failed model calls can consume credits; no success rate or model-quality conclusion is drawn from that small history.

The dependency audit reports pre-existing transitive advisories (Better Auth server OAuth/state, constrained-collection Zod, plus lower-severity development/email dependencies). This PR changes no dependencies. The app uses the Neon remote Auth proxy and Better Auth client, not a locally instantiated Better Auth OAuth server; the affected server handlers are not run here. The SDK's internal Zod schemas use fixed object fields, and the new import endpoints use the patched direct Zod 4.6.7 with bounded bodies; affected auth-UI/CLI schemas are outside this flow. The managed upstream Auth server's version has not been verified. Track its patch level and reassess the dependency graph before beta release; review date: November 11, 2026. The audit is not clean and is not evidence the remote Auth service is patched.
